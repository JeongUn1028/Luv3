# 데이트 앨범 웹 기획서

2026-11-02 작성 · 2026-11-03 보완(하단 탭 4개 화면 구조, 도메인 결정, 접근 제한·데이터 구조·열린 질문, 디자인 시안 반영, 비밀번호 로그인 전환, 사진별 한마디·정리 글, 사진 업로드 방식, 무료 플랜 일시정지 대응, 분홍 포인트 색) · 2026-11-04 보완(만든 이유, 실제 진행, 현재 기능·데이터 구조·운영 주의 반영) · 2026-11-06 보완(반복 일정·태그·지도·동시 수정·공통 창·날짜 창의 데이터 구조와 화면 설명 반영)

## 개요

둘이서만 보는 비공개 데이트 앨범을, 휴대폰에서 바로 올리고 넘겨보는 모바일 웹으로 만든다.

- **한 줄 컨셉**: 데이트 하나 = 앨범 한 장. 날짜, 장소, 사진 여러 장과 사진마다 한마디, 그날의 정리 글을 남기고 시간순으로 넘겨본다.
- **사용자**: 나와 여자친구, 단 2명. 장거리라 각자 다른 곳에서 기록을 올린다.
- **사용 환경**: 휴대폰 브라우저가 기본. PC는 같은 화면을 가운데 정렬로 보여준다.

핵심 원칙은 세 가지다.

1. **비공개가 기본**: 로그인한 두 사람 외에는 페이지도 사진도 볼 수 없다.
2. **올리기가 빠를 것**: 사진 고르고 한 줄 쓰면 30초 안에 기록 하나가 끝난다.
3. **작게 시작**: MVP를 배포해 둘이 쓰기 시작한 뒤 기능을 붙인다.

## 만든 이유

그동안 데이트 기록은 카톡으로 남겼는데, 사진과 일정을 정리하기가 불편했다. 데이트 기록 앱도 써 봤지만 가격에 비해 기능이 좋은지 모르겠다고 느꼈다. 나도 개발자이니 우리 둘이 쓸 정도는 직접 만드는 편이 낫다고 판단했다.

그래서 사진은 데이트별 기록과 앨범으로, 일정은 공유 캘린더로 모으는 것을 먼저 해결한다.

## 접근 제한

결정: Supabase 이메일+비밀번호 로그인 + 회원가입 차단 + `members` 허용목록으로 막고, 사진은 비공개 저장소에서 서명된 URL로만 보여준다.

그냥 배포하면 URL을 아는 사람은 누구나 볼 수 있고, 공개 버킷에 올린 사진은 파일 주소만으로 열린다. 그래서 페이지와 사진을 둘 다 막아야 한다.

| 방식 | 막아주는 것 | 장점 | 단점 |
| --- | --- | --- | --- |
| 공용 비밀번호 하나 | 페이지 진입 | 구현 1시간, 가입 없음 | 사진 URL은 그대로 노출, 누가 올렸는지 구분 불가 |
| Vercel 비밀번호 보호 | 사이트 전체 | 코드 수정 없음 | 유료 플랜 기능, 사진 저장소는 별도로 막아야 함 |
| **Supabase Auth + 허용목록 (채택)** | 페이지, DB, 사진 전부 | 작성자 구분, RLS로 DB 단에서 차단 | 초기 설정 반나절 |

적용할 것:

- **로그인**: 각자의 이메일 + 비밀번호(12자 이상). 로그인 후 세션을 유지해 매번 로그인하지 않게 한다. 실패하면 "이메일 또는 비밀번호가 맞지 않아요"로만 알려 어느 쪽이 틀렸는지 숨긴다.
  - 보완 이유: 처음엔 매직 링크 + 6자리 코드였으나, 매번 메일을 열어야 하고 Supabase 기본 메일 서버는 조직 멤버에게만 보내 커스텀 SMTP가 필요했다. 메일을 아예 쓰지 않도록 비밀번호로 바꿨다.
  - 비밀번호 찾기 메일은 없다. 잊으면 대시보드 SQL Editor에서 재설정한다(README "운영 Supabase 설정").
  - 비밀번호 변경: 설정에서 현재 비밀번호를 확인한 뒤 새 비밀번호(12자 이상)로 바꾼다. 같은 계정의 다른 기기 로그인은 이미 받은 접속 토큰이 끝나면(최대 1시간) 끊긴다. `secure_password_change`는 끈다: 메일을 쓰지 않는 결정과 맞고, 현재 비밀번호 확인이 같은 역할을 한다.
  - CAPTCHA(Turnstile)·TOTP 2단계 인증은 필요해지면 추가한다.
- **회원가입 차단**: Supabase Auth의 "Allow new users to sign up"을 끄고, 두 계정은 대시보드에서 직접 만든다. 앱에는 가입 화면이 없고 로그인만 요청하므로 모르는 이메일로는 계정이 생기지 않는다.
  - 보완 이유: "로그인되면 바로 로그아웃" 방식은 모르는 사람의 계정이 `auth.users`에 계속 쌓인다.
- **허용목록**: `members` 테이블에 있는 사용자만 통과한다. 계정이 있어도 `members`에 없으면 앱이 로그아웃시키고 RLS가 데이터를 막는다(이중 방어).
- **DB 보호(RLS)**: 모든 테이블에 `public.is_member()` 조건으로 select/insert/update/delete 정책을 둔다.
  - 보완 이유: 정책 안에서 `select id from members`를 직접 쓰면 `members`의 RLS가 다시 실행돼 무한 재귀 에러가 난다. `security definer` 함수로 한 번 감싼다.
- **사진 보호**: Storage 버킷 `album`을 private로 두고, 화면에 띄울 때만 만료 시간이 있는 signed URL을 발급한다. 목록은 `createSignedUrls`로 한 번에 발급한다.
- **검색 노출 차단**: `robots.txt`에 전체 Disallow, 메타 태그 `noindex`.
- **Proxy**: Next.js 16의 `proxy.ts`(15까지의 `middleware.ts`)에서 세션을 갱신하고, 비로그인 접근은 전부 로그인 페이지로 보낸다.
- **비밀값 관리**: 허용목록 이메일, Supabase 키는 리포에 커밋하지 않는다. 이메일은 Supabase 대시보드(`members` 테이블)에만, 키는 `.env.local`과 Vercel 환경 변수에만 둔다.

## 기능

MVP는 로그인, 기록 작성, 앨범 목록, 기록 상세, D-day와 공유 캘린더·홈 화면 웹앱으로 끝낸다(둘 다 2단계에서 올렸다).

| 구분 | 기능 | 내용 |
| --- | --- | --- |
| MVP | 로그인 | 허용된 두 계정만 진입 |
| MVP | 기록 작성 | 날짜(여러 날이면 기간), 제목, 장소(직접 적거나 찾아서 고르기), 사진 최대 10장과 사진마다 한마디(선택, 100자), 데이트 전체 정리 글(선택, 10,000자). 작성자 자동 기록 |
| MVP | 앨범 목록 | 대표 사진 그리드, 월별로 묶어서 최신순 |
| MVP | 기록 상세 | 사진 스와이프(넘길 때 그 사진의 한마디), 날짜·장소, 아래에 정리 글 전체, 수정/삭제 |
| MVP | D-day | 홈 상단에 사귄 날부터 며칠째인지 |
| MVP | 공유 캘린더 | 월 달력에 데이트 기록·일정·기념일, 두 사람이 함께 쓰는 일정 추가·수정·삭제, 함께 일정과 한 사람 일정 구분, 지난 함께 일정에서 기록 남기기 |
| MVP | 홈 대시보드 | D-day, 커플 사진, 최근 데이트, 일정, 하고 싶은 것을 한 화면에 |
| MVP | 커플 사진 | 두 사람이 같은 사진 한 장을 보고, 홈에서 추가·바꾸기·지우기 |
| MVP | 하고 싶은 것(Todo) | 둘이 함께 쓰는 목록, 순서 바꾸기, 완료 표시 |
| MVP | 화면 전환·로딩 | 화면을 옮길 때 움직임을 넣고, 불러오는 동안 실제 배치와 비슷한 뼈대를 보여 준다 |
| MVP | 홈 화면 웹앱 | 아이폰 Safari "공유 → 홈 화면에 추가"로 주소창 없이 앱처럼 연다. 로그인 화면에서 추가 방법을 안내하고, 닫거나 홈 화면 앱으로 열면 다시 띄우지 않는다 |
| 2단계 | 지도 | 기록 폼의 돋보기로 장소를 찾아 고르면 좌표가 함께 저장되고, 기록 탭의 지도 버튼에서 핀으로 본다. 핀에 기록이 하나면 바로 그 기록으로, 여러 개면 목록을 띄운다. 카카오맵을 쓰고, 키가 없으면 버튼이 나오지 않는다 |
| 2단계 | 댓글 | 서로의 기록에 짧은 코멘트(사진별 한마디와 별개) |
| 하지 않음 | 기념일 | 다음 기념일 표시·알림은 하지 않는다(2026-11-03 결정, #19 닫힘). 캘린더에는 사귄 날과 주년만 표시 |
| 2단계 | 태그·검색 | 기록에 태그를 5개까지 붙이고(전에 쓴 태그 추천), 기록 탭의 돋보기로 제목·장소·글·한마디·태그를 찾거나 태그로 모아 본다. 상세의 태그를 눌러도 모아 본다 |

사진은 업로드 전에 브라우저에서 두 벌로 줄여 올린다.

- **원본용**: 긴 변 2000px. 상세 화면에서 쓴다.
- **썸네일**: 긴 변 600px. 앨범 그리드에서 쓴다.
  - 보완 이유: 2000px 사진을 그리드에 그대로 띄우면 목록이 무겁고, Supabase의 이미지 변환(리사이즈)은 유료 플랜 기능이다.
- **형식**: JPEG·PNG·WebP·HEIC를 받아 둘 다 JPEG로 만든다(GIF·SVG는 받지 않는다). HEIC는 안드로이드·PC Chrome이 읽지 못해 heic2any로 JPEG로 바꾼 뒤 줄인다(HEIC를 골랐을 때만 불러온다). 원래 사진이 기준보다 작으면 키우지 않는다.
- **위치 정보**: 사진을 다시 그려 저장하므로 촬영 위치(GPS) 같은 EXIF는 남지 않는다.
- **업로드 실패**: 파일마다 한 번 더 시도하고, 그래도 실패하면 이번에 올린 파일을 모두 지운 뒤 저장 실패를 알린다. 사진이 빠진 기록이 생기지 않도록 DB 행은 업로드가 끝난 뒤 만들고, 행 저장이 실패하면 올린 파일을 지운다.

무료 저장 용량을 오래 쓰고 모바일 데이터도 아낄 수 있다.

## 화면 구성

로그인 후 첫 화면은 홈이고, 하단 탭 4개(홈 · 기록 · 캘린더 · Todo)로 화면을 오간다. 탭마다 주소가 따로 있다(`/`, `/records`, `/calendar`, `/todos`). 화면 크기는 두 사람의 기기인 아이폰 15 Pro(393×852)와 아이폰 17(402×874)에 맞춘다.

| 화면 | 내용 |
| --- | --- |
| 로그인 | 이메일·비밀번호 입력 → 로그인 |
| 홈 | 보통 때 스크롤 없이 한 화면에 담는다. 맨 위 머리글 줄 가운데에 D-day(하트·숫자·DAYS)와 오른쪽에 설정, 그 아래로 남는 높이를 채우는 커플 사진(4:3보다 작아지지 않음, 홈에서 추가·바꾸기·지우기), 정사각형 2칸(왼쪽 최근 데이트: 가장 최근 기록의 대표 사진을 가득 깔고 누르면 상세 / 오른쪽 다음 일정: 날짜와 상관없이 가장 가까운 일정 2개, 누가 만들었든, 날짜 → 종일 먼저 → 시간 → 만든 순서. 오늘 시작 시간이 지난 일정은 빼고 종일·진행 중인 기간 일정은 남긴다. 반복 일정은 하나당 가장 가까운 날 한 번만. 마지막 날에 못 넣은 일정이 있으면 "외 N개". 일정마다 2줄이고 둘째 줄에 "함께" 또는 한 사람 일정의 작성자 이름, "오늘"·"내일"·"N일 뒤", 시간과 장소를 쓴다. 작성자 이름표는 빼고 누르면 캘린더의 첫 일정 날짜), 하고 싶은 것 한 줄 카드(맨 위 3개를 가로로 잇고 넘치면 "…", 누르면 Todo). 칸마다 따로 불러와 한 칸을 못 불러와도 나머지는 보인다. 오른쪽 위 톱니바퀴로 설정 |
| 기록 | 월별로 묶은 2열 사진 그리드. 오른쪽 위에 찾기(돋보기), 지도(카카오 지도 키가 있을 때만), 작성(+) 버튼 |

로그인하면 홈으로 들어오고, 하단 탭을 눌러 기록·캘린더·Todo로 간다(스와이프 없음). 기록 탭에서 사진을 누르면 상세, + 버튼을 누르면 작성 화면으로 가고, 저장하면 기록 탭으로 돌아온다. 예전 캘린더 주소(`/?view=calendar`)로 들어오면 `/calendar`로 넘긴다.

화면을 옮길 때는 상세·작성으로 들어가면 오른쪽에서 밀려 들어오고, 화면의 뒤로 버튼과 저장·삭제 뒤에는 왼쪽에서 밀려 들어오며, 탭끼리는 하단 탭을 그대로 두고 위쪽만 살짝 바뀐다. 브라우저 뒤로 가기와 iOS 가장자리 밀기에는 움직임을 넣지 않고, 모션 줄이기 설정이면 움직임을 모두 끈다. 탭의 스크롤 위치는 다른 곳에 다녀와도 유지하지만 메모리에만 두므로 앱을 끄거나 새로고침하면 처음으로 돌아간다. 지금 탭을 다시 누르면 맨 위로 올라간다.

화면의 뒤로 버튼은 앱 안에 이전 화면이 있으면 그 화면으로 되돌아가 뼈대 없이 바로 보여 준다. 그 화면을 받은 지 30초가 지났으면 뒤에서 새로 불러와 상대가 고친 내용을 맞추므로, 30초 안에 돌아오면 그사이 상대가 고친 내용은 다음에 새로 불러올 때 보인다. 주소로 바로 들어왔거나 다른 앱에서 들어와 돌아갈 곳이 없으면 정해진 주소로 간다. 저장·삭제 뒤에는 지금처럼 결과 화면으로 옮겨, 지운 화면으로 돌아가지 않는다.

## 디자인 방향

검정 배경 위에 사진이 떠 보이는 다크 톤 앨범: 어두운 여백, 둥근 제목 글자, 장식 최소화. 라이트 모드 없이 다크 단일 테마로 간다.

- **컬러**: 배경 #0A0A0A, 입력창 같은 면 #161616, 하단 탭바 #121212, 구분선 #2A2A2A, 글자 #F2F2F2, 보조 글자 #8A8A8A, 입력 안내 글자 #6E6E6E, 포인트는 딸기우유 같은 연한 분홍 계열: 버튼·작성 버튼 #F2D2DA, 로고 하트·큰 숫자·선택된 하단 탭·캘린더의 기념일 테두리와 함께 일정 형광펜 #F5CFD9(앱 아이콘·공유 이미지의 하트도 같은 색), 영문 라벨(로그인 화면 로고 아래 SINCE, 앨범 월 제목) #C8A2AC, 작성자 이름표는 분홍 #F5CFD9 글자에 같은 색 16% 배경(닉네임 전체, 폭을 넘으면 줄임). 한 사람 일정 형광펜은 크림색 #F3E6C8로 구분한다. 달력의 일요일·공휴일은 #FF6B6B, 토요일은 #6BA8FF이고 형광펜·오늘 원·고른 날 원 위에서는 진한 #A3122A·#1D4ED8을 쓴다(글자 대비 4.5 이상). 캘린더의 기록 점은 형광펜과 구분되게 보조 글자 회색으로 둔다. 본문 글자는 읽기 편하게 분홍을 넣지 않는다. 순검정 #000과 순백 #FFF는 쓰지 않는다: OLED 화면에서 스크롤할 때 번짐이 생기고 글자 대비가 눈부시다.

- **레이아웃**: 기준 폭 393·402px(두 사람의 기기), 좌우 여백 16px(로그인 화면은 24px). 입력창·버튼 모서리 10px. 앨범 그리드는 2열(사진 비율 4:5), 그리드 간격 4px.

- **네비게이션**: 하단 탭 4개(홈 · 기록 · 캘린더 · Todo)로 화면을 오간다. 오른쪽 위는 홈이면 설정(톱니바퀴), 기록이면 찾기(돋보기)·지도(키가 있을 때만)·기록 남기기(+), 캘린더·Todo면 각자의 + 버튼(일정 추가 / 하고 싶은 것 추가).
- **창**: 삭제 확인, 커플 사진, 다시 로그인, 날짜 선택은 공통 모달(`ModalDialog`) 하나로 그린다. 네이티브 `<dialog>`라 바깥 초점을 막고 Esc로 닫히며, 화면이 숨겨지면 함께 닫혀 창이 앱을 막지 않는다. 날짜 칸은 이 모달로 만든 앱 전용 창(`DatePickerField`)이다.
- **움직임**: 넓은 버튼·카드·아이콘 버튼은 누르면 살짝 줄었다 돌아오고(눌릴 때 0.08초, 돌아올 때 0.2초), 하단 탭은 고를 때 아이콘이 살짝 튕기며 색이 부드럽게 바뀐다. 창은 아래에서 살짝 올라오며 열리고 닫힐 때 짧게 사라지며, 저장 알림은 위에서 내려왔다가 위로 사라진다. 클래스는 `press-wide`·`press-card`·`press-card-group`(칸 전체가 링크인 홈 카드)·`press-icon`이고 값은 `globals.css` 한곳에 둔다. 동작 줄이기 설정이면 움직이지 않는다.
- **참고 톤**: 어두운 갤러리 벽에 걸린 사진, 검정 하드커버 앨범. 로고의 하트 라인 말고는 이모지나 장식을 쓰지 않는다.
- **브라우저 설정**: CSS `color-scheme: dark`, `<meta name="theme-color" content="#0A0A0A">`로 휴대폰 주소창·상태바까지 검게 맞춘다.
- **홈 화면 웹앱**: `manifest.webmanifest`(standalone, 192·512 아이콘)와 애플 웹앱 메타(`black-translucent` 상태바)를 둔다. 화면이 상태바·홈 인디케이터 밑까지 채워지므로(`viewport-fit=cover`) 모든 화면의 아래쪽 고정 요소는 `env(safe-area-inset-bottom)`만큼 띄우고, 위쪽은 상태바 아래 44px까지 더 비운다(`--top-blank`). 맨 위에 시스템 흐림이 생겨 그 자리에 글자와 버튼을 두지 않기 위해서다(#127). 홈 화면 앱은 Safari와 로그인이 분리돼 처음 한 번 다시 로그인한다. 오프라인 캐시(서비스 워커)는 두지 않는다.
- **시작 화면**: 아이폰 시작 이미지는 움직일 수 없어 앱 배경색만 남기고, 앱 첫 화면 위에서 하트를 그린다(`StartupSplash`, 1.3초, 움직임은 CSS). 아래 화면을 그대로 누를 수 있고, 끝나면 없앤다. 움직임 줄이기 설정이면 나오지 않고, 앱 안에서 옮길 때(로그인·로그아웃처럼 문서를 새로 받을 때와 뒤로 가기 포함)도 다시 나오지 않는다. 로그인 화면에서는 시작 화면 대신 로그인 로고가 제자리에서 같은 순서와 시간으로 한 번 그려지고, 그린 뒤에는 완성된 채 남는다(`DrawnLogo`를 함께 쓴다). 그리는 동안에도 입력할 수 있고, 움직임 줄이기 설정이면 완성된 로고를 바로 보여 준다. 시작 이미지를 바꾸면 이미 추가한 앱은 지우고 다시 추가해야 반영될 수 있다.
- **인터넷 끊김**: 앱을 쓰다 끊기면 맨 위 빈 자리 바로 아래에 안내를 띄우고(`experimental.useOffline`), 다시 연결되면 안내를 없앤다. 끊긴 동안 탭이나 링크를 눌러도 브라우저 오류 화면으로 바뀌지 않는다. 미리 받아 둔 화면은 틀과 로딩 뼈대가 먼저 나오고, 받지 못한 화면은 지금 화면에 머문다. 둘 다 다시 연결되면 마지막으로 누른 화면으로 이어 간다. 저장은 지금처럼 실패 문구를 보여 주고 다시 누르게 한다(자동으로 다시 저장하지 않는다). **한계**: 서비스 워커가 없어 끊긴 채로 앱을 새로 켜거나 새로 고치면 브라우저 오류 화면이 나온다. #29에서 서비스 워커를 넣게 되면 이때의 안내도 함께 검토한다.

**`couple_photo`** — 홈의 커플 사진(행 하나만 둔다)

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| id | boolean | 기본키. `true`만 넣을 수 있어 두 번째 행이 생기지 않는다 |
| path | text | Storage 원본 경로 `couple/{photo_id}.jpg`. 사진이 없으면 `null`. 홈 카드용 중간 크기(긴 변 1100px)는 경로를 따로 두지 않고 옆의 `couple/{photo_id}_medium.jpg`에 둔다 |
| updated_at | timestamptz | 바꾼 시각 |

- **일정 시각**: 두 사람 모두 한국에 있어 시간대 없이 한국 날짜·시각 그대로 저장한다. 같은 날 안에서는 종일 일정이 먼저, 그다음 시각순으로 보인다.

- **Storage**: `album` 버킷, private. 읽기·쓰기 모두 `is_member()`인 사용자만 허용. 경로에는 버킷 이름을 넣지 않는다. 기록 사진은 `{date_id}/`, 커플 사진은 `couple/` 아래에 둔다.
- **RLS 정책**: `dates`·`photos`·`events` 모두 `public.is_member()` 조건으로 select/insert/update/delete 허용. `events` 추가는 작성자를 자기 자신(`author_id = auth.uid()`)으로만 할 수 있고, 고칠 때는 날짜·끝 날짜·시간·제목·장소·메모·함께 여부·반복 규칙만 바꿀 수 있다(작성자는 처음 값 그대로). 따로 나온 일정은 `detach_event_occurrence` 함수로만 만들고, `event_exceptions`는 멤버가 읽고 넣고 지울 수만 있다. `todos`도 멤버만 쓰며 추가는 내용만, 고치기는 내용·완료만 할 수 있고 순서는 `move_todo`로만 바꾼다. `couple_photo`는 읽기만 허용하고 `set_couple_photo`·`clear_couple_photo` 함수로만 바꾼다. `members`는 읽기를 허용하고, 앱에서 고칠 수 있는 것은 자기 행의 `nickname` 칸뿐이다(1~6자 검사는 화면 글자 단위라 폼이 맡고, DB는 앞뒤 공백과 20자 상한만 막는다). 행 추가·삭제와 이메일 수정은 대시보드(서비스 키)에서만 한다.
- **삭제 순서**: DB 행이 지워져도 Storage 파일은 자동으로 지워지지 않는다. 기록을 삭제할 때 앱이 그 기록의 Storage 파일을 먼저 지운 뒤 행을 지운다.
- **수정·삭제 권한**: 허용된 두 사람 모두 어떤 기록이든 고치고 지울 수 있다(작성자만으로 제한하지 않는다). 둘이 함께 쓰는 앨범이라서다.
- **수정 순서**: 새로 고른 사진만 올린 뒤 DB 함수 하나(`update_date_record`)로 글·사진 목록·순서·대표 사진을 함께 바꾸고, 뺀 사진의 파일은 그다음 지운다. 그 파일 삭제가 실패해 남는 파일은 #31(주인 없는 파일 정리)에서 치운다.
- **동시 수정**: 기록을 저장할 때마다 `revision`을 바꾸고, 고치기 화면을 연 뒤 바뀌었으면 저장을 거부한다. 오래된 화면이 상대가 더한 사진과 글을 지우지 않게 하기 위해서다. 거부되면 저장 버튼 자리에 "최신 내용 불러오기"가 나온다. 일정과 Todo에는 아직 이 확인이 없다(#161).
- **D-day 기준일**: 2026-10-31, 사귄 날을 1일째로 센다. 바뀔 일이 없는 값이라 `src/lib/anniversary.ts` 상수로 둔다. 앱 아이콘·공유 이미지에도 `SINCE 261031`로 새겨져 있어, 날짜나 로고 글꼴을 바꾸면 이미지도 다시 만든다. 시작 이미지는 앱 배경색 한 가지라 다시 만들 일이 없다.

## 운영 시 주의

- **Supabase 무료 플랜 일시정지**: 7일 동안 요청이 없으면 프로젝트가 일시정지된다. Vercel Cron이 하루 한 번(`0 3 * * *`, Hobby 플랜이라 UTC 3시대의 어느 때) `/api/keepalive`를 불러 데이터를 읽지 않는 `keepalive()` 함수만 실행한다. Vercel 환경 변수 `CRON_SECRET`이 없으면 이 경로가 모든 요청을 막으므로 Cron도 실패한다. Vercel 대시보드의 Cron Jobs에서 실행 기록을 볼 수 있지만 1시간 뒤 사라지고 실패 알림이 없어, GitHub Actions(`keepalive.yml`)가 매일 한국 시간 밤 9시 17분에 같은 경로를 따로 불러 실패하면 메일로 알린다(저장소 비밀 값 `CRON_SECRET`). 일시정지되면 대시보드에서 되살린다(README "프로젝트가 일시정지됐을 때").
- **백업**: 무료 플랜은 자동 백업을 하지 않고, 사진 파일은 DB 백업에도 들어가지 않는다. 월 1회 `pnpm backup`을 직접 실행해 개인 클라우드 드라이브에 받는다. 마지막 백업 이후의 내용은 되살릴 수 없다(README "백업과 복구").
- **DB를 바꾸는 배포**: main에 머지하면 바로 자동 배포되므로, 새 칸·함수를 쓰는 코드는 머지 전에 운영 DB에 먼저 반영한다(README "DB를 바꾸는 PR").
- **Vercel Hobby**: 비상업용 개인 프로젝트라 조건에 맞는다.
- **로그인 이메일**: 메일을 보내지 않아 로그인 아이디로만 쓴다. 받을 수 없는 주소로 만든 계정은 메일 기능(비밀번호 찾기·알림 메일)을 붙이기 전에 실제 주소로 바꾼다(`auth.users`·`auth.identities`·`members`의 email을 함께).

## 기술 스택과 일정

둘이 쓰는 무겁지 않은 서비스라, 익숙하고 개발과 배포가 빠른 Next.js에 Supabase를 붙인다.

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 프레임워크 | Next.js 16 (App Router) + TypeScript | 무거운 서비스가 아니고, 익숙하며 개발과 배포가 빠르다 |
| 스타일 | Tailwind CSS 4 | 모바일 우선 레이아웃을 빠르게 |
| 백엔드 | Supabase (Auth, Postgres, Storage) | 로그인·DB·사진 저장을 한 곳에서, 무료 티어로 충분 |
| 인증 연동 | `@supabase/ssr` | 쿠키 기반 세션, Proxy에서 갱신 |
| 이미지 처리 | browser-image-compression, heic2any | 업로드 전 리사이즈, HEIC를 JPEG로 변환 |
| 사진 넘기기 | Embla Carousel | 상세 화면 스와이프 |
| 장소·지도 | 카카오 로컬 API, 카카오맵 JavaScript SDK(둘 다 선택) | 한국 장소 검색과 지도. 키가 없으면 버튼만 나오지 않는다 |
| 테스트 | Vitest(로직), pgTAP(`supabase test db`, RLS), Playwright(대상 기기 두 크기의 화면과 주요 흐름. 평소에는 크기·배치를 재는 스펙만 두 기기에서, 나머지는 아이폰 15 Pro에서만 돌리고 main 머지 때 두 기기 전체) | RLS가 실제로 막는지, 화면이 실제로 동작하는지 자동으로 확인 |
| 배포 | Vercel (Hobby) | Next.js 배포가 가장 간단 |

처음 계획 (주말 + 평일 저녁 기준, 약 4주):

1. **1주차**: Next.js 프로젝트 생성, Supabase 테이블·RLS·private 버킷 마이그레이션, 매직 링크 로그인과 허용목록, Proxy, 검색 노출 차단.
2. **2주차**: 기록 작성 화면, 사진 리사이즈(원본·썸네일) 후 업로드, 앨범 목록 그리드.
3. **3주차**: 기록 상세(스와이프, 수정·삭제), D-day, 디자인 다듬기.
