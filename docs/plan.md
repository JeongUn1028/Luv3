# 데이트 앨범 웹 기획서

2026-11-02 작성 · 2026-11-02 보완(접근 제한·데이터 구조·열린 질문)

## 개요

둘이서만 보는 비공개 데이트 앨범을, 휴대폰에서 바로 올리고 넘겨보는 모바일 웹으로 만든다.

- **한 줄 컨셉**: 데이트 하나 = 앨범 한 장. 날짜, 장소, 사진, 짧은 메모를 남기고 시간순으로 넘겨본다.
- **사용자**: 나와 여자친구, 단 2명. 장거리라 각자 다른 곳에서 기록을 올린다.
- **사용 환경**: 휴대폰 브라우저가 기본. PC는 같은 화면을 가운데 정렬로 보여준다.

핵심 원칙은 세 가지다.

1. **비공개가 기본**: 로그인한 두 사람 외에는 페이지도 사진도 볼 수 없다.
2. **올리기가 빠를 것**: 사진 고르고 한 줄 쓰면 30초 안에 기록 하나가 끝난다.
3. **작게 시작**: MVP를 배포해 둘이 쓰기 시작한 뒤 기능을 붙인다.

## 접근 제한

결정: Supabase 매직 링크 로그인 + 회원가입 차단 + `members` 허용목록으로 막고, 사진은 비공개 저장소에서 서명된 URL로만 보여준다.

그냥 배포하면 URL을 아는 사람은 누구나 볼 수 있고, 공개 버킷에 올린 사진은 파일 주소만으로 열린다. 그래서 페이지와 사진을 둘 다 막아야 한다.

| 방식 | 막아주는 것 | 장점 | 단점 |
| --- | --- | --- | --- |
| 공용 비밀번호 하나 | 페이지 진입 | 구현 1시간, 가입 없음 | 사진 URL은 그대로 노출, 누가 올렸는지 구분 불가 |
| Vercel 비밀번호 보호 | 사이트 전체 | 코드 수정 없음 | 유료 플랜 기능, 사진 저장소는 별도로 막아야 함 |
| **Supabase Auth + 허용목록 (채택)** | 페이지, DB, 사진 전부 | 작성자 구분, RLS로 DB 단에서 차단 | 초기 설정 반나절 |

적용할 것:

- **로그인**: 이메일 매직 링크. 휴대폰 메일 앱에서 링크를 열면 다른 브라우저로 열려 세션이 안 잡힐 수 있어, 같은 메일의 6자리 코드를 입력하는 방법도 함께 둔다. 로그인 후 세션을 유지해 매번 로그인하지 않게 한다.
- **회원가입 차단**: Supabase Auth의 "Allow new users to sign up"을 끄고, 두 계정은 대시보드에서 직접 만든다. 로그인 요청은 `shouldCreateUser: false`로 보내 모르는 이메일로는 계정이 생기지 않는다.
  - 보완 이유: "로그인되면 바로 로그아웃" 방식은 모르는 사람의 계정이 `auth.users`에 계속 쌓인다.
- **허용목록**: `members` 테이블에 있는 사용자만 통과한다. 계정이 있어도 `members`에 없으면 앱이 로그아웃시키고 RLS가 데이터를 막는다(이중 방어).
- **DB 보호(RLS)**: 모든 테이블에 `public.is_member()` 조건으로 select/insert/update/delete 정책을 둔다.
  - 보완 이유: 정책 안에서 `select id from members`를 직접 쓰면 `members`의 RLS가 다시 실행돼 무한 재귀 에러가 난다. `security definer` 함수로 한 번 감싼다.
- **사진 보호**: Storage 버킷 `album`을 private로 두고, 화면에 띄울 때만 만료 시간이 있는 signed URL을 발급한다. 목록은 `createSignedUrls`로 한 번에 발급한다.
- **검색 노출 차단**: `robots.txt`에 전체 Disallow, 메타 태그 `noindex`.
- **Proxy**: Next.js 16의 `proxy.ts`(15까지의 `middleware.ts`)에서 세션을 갱신하고, 비로그인 접근은 전부 로그인 페이지로 보낸다.
- **비밀값 관리**: 허용목록 이메일, Supabase 키는 리포에 커밋하지 않는다. 이메일은 Supabase 대시보드(`members` 테이블)에만, 키는 `.env.local`과 Vercel 환경 변수에만 둔다.

## 기능

MVP는 로그인, 기록 작성, 앨범 목록, 기록 상세, D-day 다섯 가지로 끝낸다.

| 구분 | 기능 | 내용 |
| --- | --- | --- |
| MVP | 로그인 | 허용된 두 계정만 진입 |
| MVP | 기록 작성 | 날짜, 제목, 장소(텍스트), 사진 최대 10장, 메모. 작성자 자동 기록 |
| MVP | 앨범 목록 | 대표 사진 그리드, 월별로 묶어서 최신순 |
| MVP | 기록 상세 | 사진 스와이프, 날짜·장소·메모, 수정/삭제 |
| MVP | D-day | 홈 상단에 사귄 날부터 며칠째인지 |
| 2단계 | 지도 | 다녀온 장소를 지도에 핀으로 |
| 2단계 | 댓글/한마디 | 서로의 기록에 짧은 코멘트 |
| 2단계 | 기념일 | 100일 단위, 1주년 알림 |
| 2단계 | 태그·검색 | 카페, 여행 같은 태그로 모아보기 |
| 2단계 | PWA | 홈 화면에 앱처럼 추가 |

사진은 업로드 전에 브라우저에서 두 벌로 줄여 올린다.

- **원본용**: 긴 변 2000px. 상세 화면에서 쓴다.
- **썸네일**: 긴 변 600px. 앨범 그리드에서 쓴다.
  - 보완 이유: 2000px 사진을 그리드에 그대로 띄우면 목록이 무겁고, Supabase의 이미지 변환(리사이즈)은 유료 플랜 기능이다.

무료 저장 용량을 오래 쓰고 모바일 데이터도 아낄 수 있다.

## 화면 구성

앨범 홈이 중심 화면이고, 모든 화면은 폭 390px 휴대폰 기준으로 설계한다.

| 화면 | 내용 |
| --- | --- |
| 로그인 | 이메일 입력 → 메일 발송 → 링크 클릭 또는 6자리 코드 입력 |
| 앨범 홈 | 상단 D-day, 월별로 묶은 2열 사진 그리드, 하단 탭(앨범 · 작성 · 설정) |
| 기록 상세 | 화면 폭을 채우는 사진 스와이프, 날짜·장소·메모, 수정/삭제 |
| 기록 작성 | 사진 선택(최대 10장), 날짜, 제목, 장소, 메모, 저장 |

로그인하면 앨범 홈으로 들어오고, 사진을 누르면 상세, 하단 작성 버튼을 누르면 작성 화면으로 간다. 저장하면 다시 앨범 홈으로 돌아온다.

## 디자인 방향

검정 배경 위에 사진이 떠 보이는 다크 톤 앨범: 어두운 여백, 얇은 글자, 장식 최소화. 라이트 모드 없이 다크 단일 테마로 간다.

- **컬러**: 배경 #0A0A0A, 입력창·탭바 같은 면 #161616, 구분선 #2A2A2A, 글자 #F2F2F2, 보조 글자 #8A8A8A, 포인트는 아이보리 #E8E2D6 하나(D-day, 작성 버튼). 순검정 #000과 순백 #FFF는 쓰지 않는다: OLED 화면에서 스크롤할 때 번짐이 생기고 글자 대비가 눈부시다.
- **타이포**: Pretendard 하나로 통일. 날짜·제목 16~18px, 본문 15px, 보조 정보 12~13px.
- **레이아웃**: 기준 폭 390px, 좌우 여백 16px. 앨범 그리드는 2열(사진 비율 4:5), 그리드 간격 4px.
- **사진**: 모서리 라운드 없거나 4px 이하, 그림자 없음. 상세 화면은 화면 폭 꽉 채워 스와이프.
- **네비게이션**: 하단 탭 3개(앨범 · 작성 · 설정), 엄지로 닿는 위치에 작성 버튼.
- **참고 톤**: 어두운 갤러리 벽에 걸린 사진, 검정 하드커버 앨범. 이모지나 하트 장식은 쓰지 않는다.
- **브라우저 설정**: CSS `color-scheme: dark`, `<meta name="theme-color" content="#0A0A0A">`로 휴대폰 주소창·상태바까지 검게 맞춘다.

## 데이터 구조

테이블 3개와 비공개 버킷 1개로 시작한다. 스키마는 `supabase/migrations/`의 SQL이 기준이다.

**`members`** — 허용된 두 사람

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| id | uuid | 기본키, `auth.users.id` 참조 |
| email | text | 확인용(고유) |
| nickname | text | 화면에 보일 이름 |

**`dates`** — 데이트 기록

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| id | uuid | 기본키 |
| date | date | 데이트한 날 |
| title | text | 한 줄 제목 |
| place | text | 장소 이름 |
| memo | text | 메모 |
| cover_photo_id | uuid | 목록에 보일 대표 사진. 그 사진이 지워지면 `null` |
| author_id | uuid | 작성자(`members.id`), 기본값 `auth.uid()` |
| created_at | timestamptz | 작성 시각 |

**`photos`** — 기록에 딸린 사진

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| id | uuid | 기본키 |
| date_id | uuid | `dates.id`, 기록 삭제 시 함께 삭제 |
| path | text | 원본 Storage 경로 `{date_id}/{photo_id}.jpg` |
| thumb_path | text | 썸네일 Storage 경로 `{date_id}/{photo_id}_thumb.jpg` |
| sort_order | int | 사진 순서 |

- **Storage**: `album` 버킷, private. 읽기·쓰기 모두 `is_member()`인 사용자만 허용. 경로에는 버킷 이름을 넣지 않는다.
- **RLS 정책**: 세 테이블 모두 `public.is_member()` 조건으로 select/insert/update/delete 허용. `members`는 읽기만 허용하고 추가·수정은 대시보드(서비스 키)에서만 한다.
- **삭제 순서**: DB 행이 지워져도 Storage 파일은 자동으로 지워지지 않는다. 기록을 삭제할 때 앱이 그 기록의 Storage 파일을 먼저 지운 뒤 행을 지운다.
- **D-day 기준일**: 설정 값 하나라 환경 변수나 settings 테이블 한 줄로 둔다(3주차에 결정).

## 운영 시 주의

- **Supabase 무료 플랜 일시정지**: 7일 동안 요청이 없으면 프로젝트가 일시정지된다. 둘 다 일주일 넘게 안 쓰면 대시보드에서 다시 켜야 한다. 불편하면 Vercel Cron으로 하루 한 번 가벼운 요청을 보낸다(4주차에 결정).
- **로그인 메일 발송**: Supabase 기본 메일 서버는 프로젝트 조직 멤버의 이메일로만 보내고 시간당 발송량도 적다. 여자친구 이메일로 로그인 메일이 가려면 커스텀 SMTP(예: Resend 무료 플랜)를 연결하거나, 그 이메일을 조직 멤버로 초대한다(4주차 배포 전에 결정).
- **Vercel Hobby**: 비상업용 개인 프로젝트라 조건에 맞는다.

## 기술 스택과 일정

익숙한 Next.js에 Supabase를 붙여, 퇴근 후 시간 기준 약 4주 안에 MVP를 배포한다.

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 프레임워크 | Next.js 16 (App Router) + TypeScript | 이미 업무에서 쓰는 스택 |
| 스타일 | Tailwind CSS 4 | 모바일 우선 레이아웃을 빠르게 |
| 백엔드 | Supabase (Auth, Postgres, Storage) | 로그인·DB·사진 저장을 한 곳에서, 무료 티어로 충분 |
| 인증 연동 | `@supabase/ssr` | 쿠키 기반 세션, Proxy에서 갱신 |
| 이미지 처리 | browser-image-compression | 업로드 전 리사이즈 |
| 사진 넘기기 | Swiper 또는 Embla Carousel | 상세 화면 스와이프 |
| 테스트 | Vitest(로직), pgTAP(`supabase test db`, RLS) | RLS가 실제로 막는지 자동으로 확인 |
| 배포 | Vercel (Hobby) | Next.js 배포가 가장 간단 |

진행 순서 (주말 + 평일 저녁 기준):

1. **1주차**: Next.js 프로젝트 생성, Supabase 테이블·RLS·private 버킷 마이그레이션, 매직 링크 로그인과 허용목록, Proxy, 검색 노출 차단.
2. **2주차**: 기록 작성 화면, 사진 리사이즈(원본·썸네일) 후 업로드, 앨범 목록 그리드.
3. **3주차**: 기록 상세(스와이프, 수정·삭제), D-day, 디자인 다듬기.
4. **4주차**: Vercel 배포, 여자친구 계정으로 실제 사용, 불편한 점 정리.
5. **이후**: 써보면서 나온 요청 순서대로 2단계 기능 추가.
